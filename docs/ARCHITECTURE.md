# Архитектура FlowGate

## Текущее состояние и границы

Изначально был только README без Go-кода, зависимостей и Git-коммитов. Реализована одна вертикаль: YAML → validated routes → longest-prefix matcher → HTTP reverse proxy → upstream. Каждый маршрут пока имеет ровно один upstream. `cmd/flowgate` собирает зависимости явно; `internal/config` не зависит от HTTP слоя, `routing` зависит от модели конфигурации, `gateway` — от обоих. Циклических импортов нет.

`gateway.New` создаёт долгоживущие `http.Transport` на маршрут, чтобы использовать keep-alive. Контекст запроса ограничен таймаутом маршрута. Ошибки соединения дают 502, таймауты — 504. Маршруты и policy пока неизменяемы после запуска. Входные forwarding headers удаляются до передачи запроса. Клиентский request ID принимается только в коротком безопасном виде.

`/health/live` проверяет процесс; `/health/ready` проверяет TCP доступность каждого upstream и возвращает 503 при отказе. `/metrics` экспортирует общие counters/gauge без стороннего клиента Prometheus. Служебные endpoints находятся на том же listener, поэтому сеть обязана ограничивать к ним доступ.

## Расширение

Для нескольких upstream сначала ввести отдельный immutable registry и выбор цели до proxy; не менять конфигурацию во время активного запроса. Health-aware balancing должен использовать atomic snapshot состояния. Rate limiter и breaker вводятся как реальные middleware только после спецификации ключей и поведения при отказе. Retry не должен повторять тело запроса без безопасного replay.

## Риски

Проверка readiness на каждый запрос создаёт TCP соединения; при большом числе маршрутов нужен кеш с ограниченной свежестью. Не проверены WebSocket, streaming, HTTP/2 edge cases, tracing и нагрузка. Конфигурация upstream URL допускает path prefix; для будущего reload это надо документировать как совместимый контракт.
